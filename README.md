# 楽曲アナライザ

自分の楽曲ファイル（WAV / AIFF / FLAC / MP3 / Ogg / AAC など）を読み込んで、解析と編集をするブラウザツールです。インストールは不要で、音声はすべてPC内で処理されます（外部には送信されません）。

**使う: https://airman8787.github.io/music-analyzer/**

`index.html` をダウンロードして、ローカルで開いても同じように使えます。

元: [airman8787/tab-analyzer](https://github.com/airman8787/tab-analyzer)（MIT）。タブ録音を外し、ファイル専用にして編集機能を足しました。

## 2 つの画面

上のバーの「🎮 かんたん」「🎛 プロ」で切り替えます。ピッチ解析・音符と MIDI・コードと TAB 譜・信号処理の分離・ピッチ補正・音響振動解析は、上のバーの「🧰 ツール」にまとめました（機能はそのままです）。

### 🎮 かんたん（初心者向け）

1. 曲ファイルを枠にドロップします。再生に合わせて動く周波数のバー・曲全体のスペクトログラム・波形が出ます（スペクトログラムか波形をクリックすると、その位置から再生）。
2. **ジャンルのカード**を押すと、そのジャンルに合わせて自動で仕上げ、すぐ再生します。
3. **つまみ**（迫力＝100 Hz 以下・明るさ＝8 kHz 以上・広がり＝サイド・音圧＝リミッターに入れる音量）を動かすと、その場で音が変わります。ダブルクリックで 0 に戻ります。
4. 「👂 押している間だけ元の音」（<kbd>X</kbd> キーでも切り替え）で聴き比べます。元の音は統合ラウドネスをそろえて聴かせます。
5. 「配信の準備度」（音量・ピーク・PSR・音色を 25 点ずつで見た**目安**）を見て、「💾 仕上げた音を保存」。

### 🎛 プロ（自分でいじりたい人向け）

読み込みのすぐ下に「🎛 マスタリング」のラックがあります。

- **おまかせで設定**（8. の設定を使って数値を決める）か**まっさらから**始めます。
- モジュール：**EQ**（グラフの点をドラッグ＝周波数とゲイン、ホイール＝Q、ダブルクリック＝追加、<kbd>Delete</kbd>＝削除。左右 / ミッド / サイド、リニアフェーズ）、**ステレオ**（サイドの音量・低域のモノ化）、**修復**、**コンプ**（しきい値・比率・アタック・リリース）、**リミッター**（ゲイン・上限・先読み・保持・リリース。「ゲインを合わせる」で目標の統合ラウドネスに合わせる）。
- **常時メーター**：瞬間（0.4 秒）・短期（3 秒）・曲全体のラウドネス、ピーク、トゥルーピーク、PSR、再生位置でのコンプ / リミッターの圧縮量、相関。
- **スナップショット A〜D**（<kbd>1</kbd>〜<kbd>4</kbd>）、**元に戻す / やり直す**（<kbd>Ctrl</kbd>+<kbd>Z</kbd>）、**元の音**（<kbd>B</kbd>）、**自作プリセット**（コンプのしきい値は曲の大きさとの差、リミッターのゲインはおまかせとの差で保存するので、別の曲にも使えます）。
- 「🔍 仕上がりを解析」で、仕上げた音を 2.〜7. で解析し直します。

### 品質監査で直したこと

2 つの画面とリアルタイム試聴を作ったあと、画面をまたぐ操作・再生中の連続操作・変わったファイル（モノラル・5.1ch・0.5 秒・192 kHz）をまとめて試し、見つかった問題を直しました。

- **つまみを動かし続けると再生が途切れる**（音量が一定のピンクノイズで出力を取り込み、5 ms ごとの音量で確認。5 秒のうち 0.3〜1.0 秒が無音）→ 直前に送った設定の「いまの区間」と「次の区間」ができるまで次の設定を送らない・区間の残りが 1 秒未満なら次の区間もできてから切り替える。修正後は 5 回の試行で無音 0 回。動かし続けている間の音の更新は約 0.15 秒おき
- 修正の途中で入れてしまった不具合（止めるはずの予約済みの音源が残り、区切りの境目で 11 個が重なって約 11 倍の音量になる）も、同じテストで見つけて直しました
- かんたん → プロに切り替えるとラックが空のまま／仕上がりの解析後、かんたん画面の「元の音に戻す」が効かない／仕上げた音にもう一度おまかせがかかる／8. の書き出しが、ラックの未反映の設定を知らせずに元の音を出す／コーデックを通した音の試聴が無視される
- 区画の番号を詰めました（1〜8。以前の 7・9 はツールへ）。説明文も今の画面に合わせて直しました

確認：お預かりの 2 曲を、手を加えていないページ（CSP 有効）でかんたん画面から仕上げて保存し、ffmpeg（EBU R128）で測ると、どちらも −11.8 LUFS・ピーク −2.2 dBTP で、画面の表示と一致しました。CSP 違反・エラーは 0 件です。

### 🎭 サウンドステージ（各パートの位置と前後を見る・動かす）

プロ画面のラックの「🎭 サウンドステージ」、かんたん画面の「🎭 もっとこだわる」から使えます。AI（HTDemucs）で曲をボーカル・ドラム・ベース・その他に分け、舞台の絵に 4 つの玉で表示します。

- **左右**＝そのパートの左右の音量差、**前後**＝曲全体に対するそのパートの大きさ（大きいほど手前）、**玉の横幅**＝左右への広がり（サイド / ミッド）。再生に合わせて、そのパートが鳴っている瞬間に玉が脈打ちます。
- **動かす**：玉を上下にドラッグ＝前後（そのパートの音量、±6 dB まで・目安は ±3 dB）、左右にドラッグ＝左右の位置、ダブルクリック＝元に戻す。離すと音に反映します。「🎤 ボーカルを前に」「🔊 低音をはっきり」「🥁 ドラムにパンチ」のワンタッチもあります。パートが奥にいるとき（曲全体より 12 dB 以上小さい）は、一言の助言を出します。
- **仕組み**：仕上がり＝「元の音 ＋ Σ（動かした後のパート − 元のパート）」。これがマスタリングの入力になり、試聴と書き出しに同じように入ります。何も動かしていなければ元の音とまったく同じで、「元の音」ボタンは動かす前の音を鳴らします。左右は、p>0 なら左の音を右へ移します（L′=(1−p)L、R′=R+pL）。
- 分けている間も、曲の再生やつまみは使えます。分けた結果は、「仕上がりを解析」や「元の音に戻す」をしても残り、別の曲を表示したときに捨てます。

確認：動かさないときの差は 0、動かした結果は式どおり（差 6×10⁻⁸ 以下）、何もかけない設定での書き出しは作った音と一致（差 0）。合成ミックス（正解のパートが分かっているもの）では、ドラムとベースの大きさの推定が正解と 0.1 dB 以内、左右は 0.001 以内でした（この合成ミックスの「ボーカル」は声ではないので、ボーカルとその他の分離は当てになりません）。

限界：
- 分離は完全ではないので、大きく動かすほど、ほかのパートの音が混じって聞こえます。
- 「前後」は大きさからの目安で、リバーブなどによる奥行きは測っていません。「その他」にはギター・鍵盤などがまとめて入ります。
- 分離には時間がかかります（テスト環境の 4 スレッドで、16 秒の曲に約 46 秒、30 秒の曲に約 91 秒。WebGPU が使える環境ではもっと速くなります）。初回はモデル（約 180 MB）のダウンロードが必要です。
- パートを上げるとピークも上がります。リミッターを使っていないときは注意を表示します。大きく動かした後は、もう一度「おまかせ」を押すと音量が合い直ります。
- 5.1ch などは分けられません（ステレオかモノラルのみ。モノラルでは左右は動かせません）。

### おまかせの待ち時間

50 秒以上の曲では、まず曲の一部（いちばん大きい所 3 か所の前後 3 秒ずつと、均等に取った 5 か所の 3 秒ずつ、計約 33 秒）だけで数値を決めて再生を始め、裏で曲全体の計算を続けて、終わったら自動で差し替えます（25 ms のクロスフェード）。計算は専用の Worker で行い、別のジャンルを選んだり曲を替えたりすると途中で止めます。

- カードを押してから音が出るまで：15〜19 秒 → **約 3.5〜4.8 秒**（お預かりの 2 曲・テスト環境での値）
- 先に鳴らす設定と最終の設定の差：リミッターのゲインで 0.25〜0.55 dB、コンプのしきい値で 0.35〜1.2 dB
- 先に鳴らしている間に動かしたつまみは、差し替えの後も残ります。保存と「仕上がりを解析」は、曲全体の計算が終わってから実行します（押しておけば、終わりしだい進みます）
- 曲全体の計算が終わるまで 20〜24 秒、準備度の点数が出るまで 33〜49 秒かかります（プロ画面のラックの調整は、曲全体の計算が終わってから）

### 試聴している音と保存する音は同じです

動かすたびに曲を約 2.4 秒ずつ区切り（前 3 秒・後 0.5 秒の余白つき）、専用の Worker で処理し直して、再生中の音を 25 ms のクロスフェードで差し替えます。書き出しも同じ区切り・同じ関数で処理します。曲全体の統計で決まる値（コンプのしきい値・耳に痛い瞬間の基準・音割れ修復の基準・リミッターのゲイン）は、おまかせのときに確定した数値として持ちます。

確認した結果：
- 確定した数値だけで処理し直した音は、おまかせの処理とビット単位で一致（2 曲 × 最小位相 / リニアフェーズ）。
- 区切って処理した音と通しで処理した音の差は、最大 −112.9 dBFS（信号に対して −136 dB 以下）。
- 再生中の音を音声スレッドで取り込むと、区切りの境目をまたいでも、処理した音と一致（差 6×10⁻⁸ 以下）。数値を変えたときも、差し替えの前後でそれぞれ元の設定・新しい設定の音と一致し、時間のずれはありませんでした。
- つまみを動かしてから新しい音が予約されるまで約 0.1 秒、元の音への切り替えは約 0.01 秒（テスト環境での値）。
- 再生は曲と同じサンプルレートで行います（違うと区間ごとにブラウザが変換し、つなぎ目がわずかに乱れるため）。

### ジャンルの音色の目安について

すべてのジャンルの目安の土台（「汎用の目安」）の **100 Hz〜2 kHz の形** は、Elowsson & Friberg (2017) "Long-term Average Spectrum in Popular Music and its Relation to the Level of the Percussion"（AES 142nd Convention, Paper 9762）の、ポピュラー音楽 12,345 曲の平均の長時間スペクトルの近似式（式 5・6）から作っています。

- 周波数軸は x = 1 + 60·log₂(f/30)（30 Hz から 1 オクターブを 60 等分。x=100 が 94 Hz）。この定義で、論文の表 1 の傾き（200 Hz で −2.350 … 6.4 kHz で −8.938 dB/オクターブ）が小数第 3 位まで再現できることを確かめました。
- 式 5 の p₁ は紙面では「0.000907」と読めますが、論文の「2 つの式を x=100 で交わるように調整した」という記述を満たすのは −0.000907 です（正だと x=100 で +1.7 dB、負だと −16.4 dB で式 6 の −16.4 dB と一致）。負の値を使っています。
- 論文の値は 1 Hz あたりの強さなので、このツールの 1/6 オクターブ帯のエネルギーに直すため 10·log₁₀(f) を足しています。
- **100 Hz〜2 kHz に限った理由**：論文 5 節（図 9）で、打楽器の量が近い曲だけで目安を作ると誤差が減ったのは 100 Hz より下と 2 kHz より上で、中域は全曲の平均でもほぼ同じ精度だったためです。論文は、ジャンルによる低域・高域の違いは主に打楽器の量の違いによると結論づけており、データもフォーク寄りです（2.1 節）。そのため低域・高域は平均をそのまま使わず、従来の形を論文の 100 Hz・2 kHz の値につないでいます。
- この変更で、目安の 100 Hz より下は、中域に対して以前より約 4.6 dB 低くなりました（中域の形の変化は −0.5〜+1.4 dB）。手持ちの 2 曲では、おまかせの低域のシェルフが +2.1 → +1.3 dB、−0.6 → −2.1 dB に変わりました（J-POP）。
- ジャンルごとの上げ下げ（低域・2〜5 kHz・高域）と音量は、論文にジャンル別の数値がないため、従来どおり**大まかな目安**です。

好きな曲に近づけたいときは、その曲を「好きな曲に寄せる」（かんたん）・8. の「寄せる先」（プロ）に選ぶか、7. に保存して 5. でターゲットを作ってください。

## はじめかた

1. 「1. 読み込み」の枠に音声ファイルをドロップするか、「ファイルを選ぶ」で選びます。**何曲でもまとめて入れられます。**
   - 1 曲目が A として 2.〜8. に表示され、残りの曲も順番に自動で解析されて「曲リスト」に並びます（ラウドネス・ピーク・PLR・PSR・LRA・BPM・キー・チェック結果）。
   - リストの「A で表示」（または曲名のクリック）で、その曲の詳しい結果に切り替わります。
   - 「解析した曲を 7. に保存（音声つき）」にチェックすると、解析した曲が 7. の保存一覧にも入ります。一覧は CSV で保存できます。
2. 「2. 概要」と「3. 公開前チェック」で、音圧・ダイナミクス・周波数バランスなどの結果と対処のしかたを見ます。
3. 「4. 波形」はクリックで再生、ドラッグで範囲を選べます（選んだ範囲は、編集や書き出しの対象にできます）。

## アルバムとしてまとめて仕上げる（1. の曲リスト）

曲リストに入れた全曲に、8. の「おまかせマスタリング」と同じ仕上げをかけて、ZIP（FLAC 24bit / WAV 24bit / WAV 16bit）で保存します。ファイル名は `01_曲名_master.wav` のように曲順の番号付きです。

- 「全曲の音量をそろえる」（おすすめ）：まず各曲をジャンルの目安で仕上げ、いちばん小さく仕上がった曲（音質優先で止まった曲を含む）の音量に、0.5 dB 以上大きい曲を合わせて仕上げ直します。後から音量を下げるより、リミッターのかかりが浅くなるためです。
- 「各曲ともジャンルの目安に合わせる」：曲ごとに目安どおり仕上げます（音質優先で止まった曲は小さめになります）。
- 確認：60 秒の 3 曲（性格の違う曲）を EDM の目安で仕上げ、保存した ZIP を展開して計測すると、音量の差は最大 0.16 dB、トゥルーピークはすべて −1 dBTP 以下でした。

## A/B 比較（2曲を聴き比べる）

1. 「1. 読み込み」の曲リストで、比べたい曲の「B で比べる」を押します。最初に 2 曲だけまとめて入れたときは、自動で A と B に入ります。
2. 上のバーの ▶ / A / B ボタン、または `X` キーで切り替えます。
3. 公平に比べるときは、試聴音量を「ラウドネス一致」にしてください（大きい音のほうが良く聞こえやすいためです）。

- 切り替えても再生位置は同じままで、前後の無音をトリムした状態で頭がそろいます。ループ再生中も切り替えられます。
- B の再生中も波形に再生位置が出て、クリックするとその位置へ移動します。
- 上のバーに「B は A より -7.5 dB」のように音量差が出ます。
- B は保存されず、ページを閉じると消えます。残したい曲は、A として読み込んで「7. 保存して比較」で保存してください。

## おまかせマスタリング（かんたん画面の「音を良くする」／プロ画面の 8. の最初のタブ）

ジャンルを選んで実行すると、曲全体に次の順で処理をかけます（プロ画面では、各段のオン・オフと強さを変えられます）。

1. **オート EQ**：「ジャンルの目安」か「5. で選んだターゲット（好きな曲から作ったもの）」との音色の差を、約 1 オクターブで平滑化し、帯域を固定した幅の広い 5 バンド（90 Hz シェルフ・250 Hz・800 Hz・2.5 kHz・8 kHz シェルフ）の最小二乗で補正します（最大 ±3 dB × かかり具合）。曲のキーや楽器の音程による細かい山谷は追いません。20 Hz 以下の超低域カットもかけられます。
2. **低域のモノラル化**（自動：低音が左右に広がりすぎのときだけ）：サイドからゼロ位相の 4 次ローパス成分を引き、120 Hz 以下の左右差だけをなくします。上の帯域の位相とステレオ感は変わりません。
3. **耳に痛い瞬間を抑える**（試験的・既定はオフ）：4.2 kHz 付近が中域と比べて突出した瞬間だけ下げるダイナミック EQ。
4. **オートコンプ**：左右連動の RMS 型。しきい値は曲の大きい部分から自動で決め、そこで約 1.5 / 2.5 / 4 dB 圧縮します（弱め / ふつう / 強め）。
5. **リミッター**：4 倍オーバーサンプリングでピークを検出する先読みリミッターで、目標の統合ラウドネスに合わせます。最後に解析と同じ精密なトゥルーピークで確かめ、上限を超えていたら補正します。上限の既定は、Spotify の推奨に合わせて、目安が −14 LUFS より大きいジャンルでは −2 dBTP、それ以外は −1 dBTP です。
6. **音質優先**（既定オン）：PSR（曲の大きい部分のピークと短時間ラウドネスの差）が 8 dB 以上、最大ショートタームラウドネスが −10 LUFS 以下（3. の公開前チェックと同じ目安）に収まるところで、音量を上げるのを止めます。元の曲がすでにこの目安を超えている（潰れ気味・大きい）ときは、基準を「元の曲より潰さない・大きくしない」に置き換えます（PSR は元 −0.5 dB、最大ショートタームは元の値まで）。下げても、すでにかかった潰れは戻らないので、音量を無意味に下げないためです（仕上げ後の解析で目安を割らないよう、0.2〜0.3 dB の余裕を持たせます）。止めたときは、その理由と止めた値を表示します。配信サービスは −14 LUFS 前後にそろえて再生するので、それ以上大きくしても大きくは聞こえません。

   実際の曲（Suno で作った 2 曲・MP3）で、J-POP の目安で仕上げたときの結果：

   | | 音量 | PSR | 最大ショートターム | Opus 96 kbps に変換後のピーク |
   |---|---|---|---|---|
   | 曲 1（処理前） | −14.8 LUFS | 10.1 dB | −12.7 LUFS | −2.6 dBTP |
   | 曲 1（以前の版：PSR だけを見ていた） | −10.6 LUFS | 7.9 dB（潰れ気味の警告） | −8.7 LUFS（警告） | −0.4 dBTP（−1 超え 3 か所） |
   | 曲 1（今の版） | −12.0 LUFS | 9.2 dB | −10.3 LUFS | −1.1 dBTP |
   | 曲 2（処理前） | −15.3 LUFS | 10.0 dB | −12.5 LUFS | −2.1 dBTP |
   | 曲 2（今の版） | −11.9 LUFS | 9.3 dB | −10.3 LUFS | −0.4 dBTP（−1 超え 1 か所） |

### リファレンス曲に寄せる

「寄せる先」に、1. の曲リストの曲（解析が終わったもの。A で表示中の曲は除く）、「B で比べる」で入れた曲、7. に保存した曲のどれかを選ぶと、ジャンルの目安の代わりにその曲を目標にします（かんたん画面・8.・アルバム仕上げで共通）。

- **音量**：その曲の統合ラウドネス（−24〜−5 LUFS の範囲）。上限は Spotify の推奨どおり、−14 LUFS より大きければ −2 dBTP。音質優先はそのまま働くので、リファレンスが潰れ気味の曲だと手前で止まります。
- **音色**：その曲の 1/6 オクターブの音色との差を、オート EQ で控えめに補正します。
- **ステレオの広さ**：サイド / ミッドのエネルギー比の差を、サイドの音量で ±3 dB まで合わせます。
- コンプの強さはジャンルの設定を使います。
- 確認：リファレンス（−18.0 LUFS・広さ −11.8 dB）に寄せると、仕上がりは −18.0 LUFS、広さの差 6.3 dB → 2.4 dB、音色の差は低域 2.2 → 1.2 dB・高域 −2.2 → −1.5 dB でした。

LANDR の資料にもあるとおり、権利を持っていない曲をリファレンスとしてアップロードすることには注意が必要です（このツールでは曲は外部に送信されません）。

### 音割れ（クリップ）の修復

波形の頭が平らに切れた所（最大値付近が 2 サンプル以上続く所）を、前後の音から最小二乗 AR 補間（Janssen ほか 1986）で作り直します。本当の値は「クリップの高さ以上・同じ符号」のはずなので、それを満たさないサンプルはクリップの高さに固定して、残りを解き直します。

- 8. の「修復」タブで単独に使えるほか、おまかせ仕上げでは、音割れが見つかった曲だけ自動で最初に修復します（フィルタを通すと平らな頭の形が崩れるため、すべての処理の前）。
- 修復タブで直した場合は、直した波形が元のピークを超えるので、元のピーク以下になるよう全体の音量を下げます。

テスト信号を 3 / 6 dB クリップさせ、元の音との誤差（クリップした所）がどれだけ小さくなったか：

| 素材 | 3 dB クリップ | 6 dB クリップ |
|---|---|---|
| 和音（3 つの正弦波） | 25.6 dB 改善 | 19.5 dB 改善 |
| ベース＋キック＋小さいノイズ | 13.5 dB 改善 | 3.5 dB 改善 |
| ピンクノイズ＋キック | 1.1 dB 改善 | 2.5 dB 改善 |
| 合成ミックス（クリップ部分の主成分がノイズのスネア） | 0.0 dB（変化なし） | 0.0 dB（変化なし） |

ノイズのような音（スネア・シンバルなど）の削れた部分は前後から予測できないので、原理的にほとんど戻せません。低音の山（キック・ベース）はよく戻ります。悪化した例はありませんでした。3 次曲線で山を描く方法も試しましたが、多くの素材で AR 補間より悪かったので採用していません。

### パート別の音量（8. の「パート別の音量（AI）」タブ）

AI（Meta の HTDemucs）で、曲をボーカル・ドラム・ベース・その他の 4 つに分け、それぞれの音量を変えます（例：ボーカルだけ +2 dB）。分けたパートは WAV で書き出せます。

- 仕上がりは「元の音 ＋ Σ（ゲイン − 1）× 各パート」。すべて 0 dB なら元の音とまったく同じで、AI が分けきれなかった成分も失われません。
- 初回だけ、モデル（180,534,758 バイト）を Hugging Face からダウンロードし、SHA-256 で照合してからブラウザ（IndexedDB）に保存します。次回からはダウンロードしません。**音声はどこにも送信しません。** 実行には [ONNX Runtime Web](https://onnxruntime.ai/) 1.20.1 を jsDelivr から読み込みます（この機能を使うときだけ）。
- 推論は Web Worker で行います（画面は固まりません）。WebGPU が使えれば WebGPU、使えなければ WASM（CPU）。
- **複数スレッド**：公開ページ（https）や localhost で開いたときは、同梱の Service Worker（`coi-sw.js`）がページに COOP / COEP のヘッダーを付けて「クロスオリジン分離」にし、WASM を CPU のコア数（最大 8）のスレッドで動かします（初めて開いたときだけ 1 回自動で再読み込みします）。`index.html` を直接開いたときは Service Worker が使えないので 1 スレッドです。Service Worker はヘッダーを足すだけで、何もキャッシュせず、外部への通信には触れません。
  - 確認（4 コア・16 秒の合成ミックス）：1 スレッド 59.1 秒 → 4 スレッド 25.1 秒。分離の結果は同じ。ONNX Runtime は本物の jsDelivr から（jsDelivr は CORS と `Cross-Origin-Resource-Policy: cross-origin` を返すので、分離の状態でも読み込めます）、モデルは Hugging Face から取得できることも確認しました。
  - WebGPU：この開発環境には GPU がなく、WebGPU での速さと結果は未確認です（ソフトウェアの WebGPU では 30 分以上終わらず中止しました）。44.1 kHz 以外の曲は、このツールの高品質なサンプルレート変換で 44.1 kHz にして分け、元に戻します。
- モデル：[HTDemucs](https://github.com/facebookresearch/demucs)（Meta・MIT）を [demucs-web](https://www.npmjs.com/package/demucs-web)（timcsy・MIT）が ONNX にしたもの。配布元は [ptasior/pizu-audio-models](https://huggingface.co/ptasior/pizu-audio-models)（元のファイルと同じ SHA-256 と明記されたミラー、固定リビジョン `74331d1e`）。STFT と逆 STFT は demucs-web と同じ約束事で、このツールで実装しています。

確認したこと：

- STFT → 逆 STFT：正弦波で 164 dB 一致（区間の中央）。区間の端の誤差は、区間を 25% 重ねてつなぐ重みでほぼ消えます。
- 正解の分かっている合成ミックス（16 秒）を分けた SDR：ドラム 23.7 dB・ベース 20.6 dB・その他（合成の和音）−5.8 dB・ボーカル（合成の母音）1.8 dB。4 パートの合計は元の音と 32.4 dB 一致。Node（onnxruntime-node）とブラウザ（onnxruntime-web・WASM）で同じ値でした。合成の和音や母音は本物の楽器・声とかけ離れているため、低い値は実際の曲での性能を表しません（実際の曲での評価はまだしていません）。
- 速さ：16 秒の音を、ヘッドレスの Chromium（WASM・CPU）で約 55 秒（曲の長さの約 3.5 倍）。WebGPU での速さは、確認できる環境がなく未確認です。
- 中止はすぐ効き（Worker ごと終了）、2 回目以降は保存したモデルを使う（ダウンロード要求 0 件）ことを確認しました。

### 試して見送ったもの：AI 曲の高域のシャリシャリ（shimmer）対策

高域（6〜16 kHz）の成分が時間方向に細かく明滅するのを抑える処理を 2 通り・6 設定試しました。人工の明滅を足した音での改善（きれいな音との距離 4.33 → 3.84〜4.06 dB）と同じくらい、明滅のないきれいな音も変えてしまう（0.70〜1.90 dB）ため、音質を下げるおそれがあると判断して入れていません。

### 上級者向けの調整（プロ画面の 8. →「上級者向けの調整」）

- **手動 EQ**：バンドごとに種類（ピーク・シェルフ・ハイパス・ローパス）・周波数・Q・ゲインと、かける対象（左右 / ミッド / サイド）を指定できます。「オート EQ の提案を表に入れる」で自動の提案から始めて細かく直せます。設定はブラウザに残ります。周波数特性のカーブを左右・ミッド・サイド別に表示します。
- **リニアフェーズ（ゼロ位相）**：各段を前向きと後ろ向きに通して位相のずれをなくします（書き出し前のオフライン処理なので可能）。打楽器の前に小さなプリリンギングが出ることがあります。
- **コンプの数値指定**：比率・圧縮量（曲の大きい部分での目標ゲインリダクション）・アタック・リリース。
- **リミッターの数値指定**：先読み・保持・リリース（最短〜最長）。
- **処理後のグラフ**：コンプとリミッターが「どこで、どれだけ抑えたか」の時間変化（50 ms ごと）と、処理前・処理後・目安の音色の重ね表示。

## 配信・納品の条件（3. 公開前チェックの下）

読み込んだファイルのヘッダ（WAV / AIFF / FLAC）から、ビット深度・整数か浮動小数点か・サンプルレートを読み、各社の公開資料の条件と照らします。

| 配信先 | 項目 | 条件（出典） |
|---|---|---|
| Spotify | 音量 | −14 LUFS にそろえて再生（[Loudness normalization](https://support.spotify.com/us/artists/article/loudness-normalization/)） |
| Spotify | トゥルーピーク | −1 dBTP 以下。−14 LUFS より大きいマスターは −2 dBTP 以下（同上） |
| Apple Digital Masters | ビット深度 | 24bit PCM。16bit を 24bit にした水増しは不可（[Apple Video and Audio Asset Guide](https://help.apple.com/itc/videoaudioassetguide/en.lproj/static.html)） |
| Apple Digital Masters | サンプルレート | 44.1 / 48 / 88.2 / 96 / 176.4 / 192 kHz、アップサンプル不可（同上） |
| Apple Digital Masters | トゥルーピーク | −1 dBTP 以下（BS.1770-4）（同上） |
| CD（Red Book） | 形式 | 16bit・44.1 kHz・ステレオ |

- **水増しの検出**：24bit のファイルでも、全サンプルが 16bit の格子に乗っていれば「実際は 16bit の音」と判定します。
- **アップサンプルの検出**：88.2 kHz 以上のファイルで、22 kHz 付近より上が急に空になっていれば「アップサンプルの可能性」と判定します（高域まで音がある本物の 96 kHz では出ないことを確認）。
- 確認：本物の 24bit・16bit の水増し・96 kHz へのアップサンプル・32bit float・16bit の各テストファイルで、期待どおりに判定されました。

## トゥルーピークの測り方

BS.1770 の 4 倍オーバーサンプリングでピークのありそうな位置を探し、その近くを ±128 タップのカイザー窓 sinc で 1/16 サンプル刻み（＋放物線補間）まで細かく補間して求めます。4 倍の格子では高域の強い音で読み落とすためです。

- 以前の版は、候補を 200000 か所で打ち切っていたこと、また強くクリップした広帯域ノイズでは BS.1770 の 4 倍 FIR が想定より低く読むことから、最大 0.47 dB 読み落とすことがありました（合成信号での確認）。
- 今の版は打ち切りをなくし、候補の幅を広げたうえで、まず 1/4 サンプル刻みの 3 点だけを精密に計算し、1/cos(π/8) を掛けても今の最大に届かない位置は細かい計算を省いて速くしています。
- 合成信号 400 通り（ナイキスト付近の正弦波・ホワイトノイズ・クリップしたノイズ・矩形波・インパルス・チャープ、半数はリミッター通過）で、全数計算に対して読み落としがないことを確認しました。
- 速さ（ブラウザ・1 チャンネル）：リミッターで強く潰した 3 分の音で 6.5 秒 → 2.8 秒、60 秒のマスター音源で 0.94 秒 → 0.79 秒。

## 再生機器のシミュレーション（上のバーの「再生機器」）

スマホのスピーカー・ノートPC・安いイヤホン・車のスピーカー・テレビ・モノラルで聴いたときの音を、EQ（とスマホ・モノラルでは左右を混ぜる処理）で大まかに真似て再生します。A / B どちらにもかかります。

- **実機を測ったデータではありません。** 小さいスピーカーは低音が出ない、中高域が目立つ、といった一般的な傾向を、私が設定した EQ で近似したものです（市販の MixChecker などは実機の測定にもとづくとしています）。低音が消えてベースが聞こえなくならないか、ボーカルが埋もれないか、といった大きな問題の確認向けです。
- 確認：オフラインでノイズを通して測ると、設計した特性との差は 200 Hz 以上で 0.1 dB 以内でした。
- 起動時は毎回「そのまま」に戻ります（気づかずに近似の音で判断しないように）。

## 書き出し

WAV 24bit / WAV 16bit（TPDF ディザ・CD 向け）/ WAV 32bit float / FLAC 24bit / FLAC 16bit（ディザ）。FLAC はビット単位で WAV と同じ値になることを確認しています。

サンプルレートは「元のまま / 44.1 / 48 / 88.2 / 96 kHz」から選べます（8. の書き出し）。かんたん画面とアルバム仕上げの「CD 用」は、16bit・44.1 kHz に変換して書き出します。16bit のディザは変換の後にかけます。

### サンプルレート変換

窓付き sinc（カイザー窓・減衰 140 dB）の有理比の多相フィルタです。出力レート / 入力レートを約分した L/M の L 通りの位相の係数を前もって計算するので、位相の近似がありません。通過帯域は 20 kHz まで、阻止帯域は低いほうのナイキスト周波数から。ツール内の変換（AI 分離・コーデック確認・結合）もすべてこれを使います。

| 項目 | ブラウザ標準（Chrome の OfflineAudioContext） | このツール |
|---|---|---|
| 48 → 44.1 kHz の 10 kHz / 20 kHz | −1.26 dB / −5.28 dB | 0.000 dB / 0.000 dB |
| 23 kHz の折り返し（→ 21.1 kHz） | −7.1 dB | −148.6 dB |
| 44.1 → 48 kHz の像（21 kHz → 23.1 kHz） | — | −183.2 dB |
| 理想の正弦波との誤差（1 kHz / 19 kHz） | — | −148.2 / −143.1 dB（float32 の丸めの限界は −153.8 dB） |
| 4 分 26 秒のステレオ（48 → 44.1 kHz）の変換時間 | — | 2.4 秒（ブラウザ・4 コアで並列。1 本だと 8.3 秒。結果はビット単位で同じ） |

- 実際の曲（48 kHz の MP3）を 44.1 kHz・16bit で書き出すと、統合ラウドネスとトゥルーピークは ffmpeg の測定で元と同じ（−14.8 LUFS・−2.8 dBTP）、40 Hz〜18 kHz の帯域ごとのパワーの差は 0.003 dB 以内でした。
- 以前の版は AI 分離などでブラウザ標準の変換を使っていました。同じ曲の AI 分離で、4 パートの合計と元の音の一致が 25.3 dB → 30.4 dB に上がりました。

## セキュリティ

- **外部から読み込むものは中身を照合してから使います**：AI のパート分離で使う ONNX Runtime Web（jsDelivr の 3 ファイル）とモデル（Hugging Face）は、大きさと SHA-256 が、あらかじめ確認しておいた値と一致したときだけ使います。一致しないとき（改ざんや配信の不具合）は「使用を中止しました」と表示して止まります。照合したバイト列そのものを blob から読み込むので、照合のあとで別の中身にすり替わることもありません。
  - 確認：1 バイトだけ書き換えた `.mjs` を読ませると拒否、ファイルが無いときも HTTP 404 として止まり、画面はそのまま使えました。本物の jsDelivr からは従来どおり読み込め、分離の結果（SDR）も変更前と同じでした。
- **CSP（Content-Security-Policy）**：ページに埋め込んだ 2 つのスクリプト（SHA-256 で指定）以外のスクリプトは動きません。通信できるのは自分自身・jsDelivr・Hugging Face だけです。
  - 確認：後から差し込んだ `<script>`、`onerror` などの属性、外部のスクリプト、`eval`、ほかのサイトへの `fetch` がすべて止められ、通常の機能（解析・おまかせ・書き出し・レポート・AI 分離 4 スレッド）では違反が 0 件でした。
  - **`index.html` のスクリプトを編集したら `python3 tools/update-csp.py` を実行してください**（ハッシュが合わないとページが動きません。`--check` で確認だけできます）。
- **保存データの読み込み**：JSON は決まった項目だけを型を確かめながら作り直します（余計なキーや `__proto__` は取り込みません）。曲名などの文字列は画面に出すときに必ずエスケープしています。
- 音声はどこにも送信しません。

### 変わったファイルでの確認

空のファイル・テキスト・ランダムなバイト列・ヘッダーだけのファイル・途中で切れたファイル・0.05 秒 / 0.5 秒・無音・直流（DC）だけ・8bit・モノラル（WAV / MP3）・8 kHz・192 kHz / 24bit・0 dBFS を超える 32bit float・5.1ch で、読み込み → おまかせ → 書き出し（→ モノラル・5.1ch・0.5 秒は AI 分離も）を試し、見つかった問題を直しました。

- 無音のファイルで画面が固まる（グラフの目盛りが無限に続く）→ 修正
- 壊れて数ミリ秒しか読めないファイルを、そのまま解析して意味のない値（調・PLR ∞ など）を出す → 0.4 秒未満は理由を示して読み込まない
- 無音・直流だけの音を「仕上げ」て、クリック音だけのファイルができる → 処理前に止める
- 192 kHz の曲でテンポを半分（120 → 60 BPM）に間違える → 解析の窓の長さをサンプルレートに合わせて修正（44.1 / 48 kHz の結果は変わりません）。5 秒未満の音ではテンポを出さない
- 同じ曲なのに長さによってテンポが 60 / 120 BPM に割れる（10 秒の MP3 で発覚。原因は MP3 ではなく、キックとスネアが交互の曲で「半分のテンポ」と僅差になる採点）→ 同点のときの優先範囲をおよそ 88〜177 BPM に狭めて修正。テンポの分かっている合成パターン 312 通りで正解 190 → 212、長さで結果が変わる組は 0。残る誤りは 80 BPM 以下（2 倍に出る）と 174 BPM 以上（半分に出る）で、画面には「半分 / 倍」の値も併記しています
- 曲リストにまとめて入れたとき、1 曲目が壊れていると何も表示されない → 次に読める曲を表示
- 読めないファイルのエラーを英語ではなく日本語で説明
